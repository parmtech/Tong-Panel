## Status and unresolved decisions

P0 remains active. The roadmap's P0 exit requires approved architecture ADRs, a reviewed threat model, fixed P1 scope and distro matrix, and an explicit go/no-go. At the inspected P1 baseline, `docs/ADR_REGISTER.md` still marks ADR-001–008 as proposals; the initial threat model remains unreviewed. `docs/ADR-009-AUTHENTICATION.md` exists at the exact P1 head but is also **PROPOSED**, with no production login/credential store authorization. The P1 exit report says P1 is incomplete and P2 entry is blocked.

This draft makes no ADR choice. It keeps the following unresolved until written owner/security decisions are recorded in the canonical ADR/issues:

- Control plane language/service boundary, storage and durable-job semantics, execution profiles, least-privilege boundary, secrets custody, package signing and provenance.
- Supported Linux distro/version/architecture matrix. Ubuntu 24.04 x86_64 and Debian 12 x86_64 are candidate lab targets only; no distro is certified. Debian 13, arm64, AlmaLinux and Rocky remain out of scope until separately reviewed and tested. There is a source-document mismatch to resolve under P0-07: INSTALLER_SPEC lists Debian 12/13 with Ubuntu 24.04 as initial validation candidates, while ADR-005 and TEST_STRATEGY place Debian 13 after verified CI. The scope decision must reconcile these texts before any support promise.
- Numeric minimum CPU, RAM, free disk, concurrency and supported runtime versions. The reviewed blueprint/specs provide no approved general-purpose minimum; P1 must not invent one. The proposed ADR-009 Argon2id profile of 64 MiB, 3 passes and 4 lanes is explicitly unapproved and unbenchmarked; test KDF concurrency/latency on the smallest owner-approved VM before adopting it. Security-sensitive operations (including password KDF, queue load and build/profile limits) need measured bounds against the approved test profile before a support claim.
- Which production authentication, recovery, backup encryption/key custody and privileged-agent policies are acceptable.
- P4 provenance/licence review results and any P2 security/test-design findings that constrain P1 interfaces. These handoffs are requested below; this draft is **not final** until reconciled with their verified hub events.

## Scope boundary

P1's minimum deliverable is a reviewed, testable foundation that hosts zero customers: repository/CI and API contract; identity, tenant and authorization model; safe authentication/session/MFA/recovery policy; durable auditable jobs; a narrowly typed local agent boundary; metadata/migration and metadata-store snapshot/restore contract only (not customer/site/offsite backup lifecycle); integrated UI shell and diagnostics; and a signed, provenance-tracked experimental package plus clean disposable-VM evidence. The agent/installer must remain gated until the relevant ADR and threat-review evidence is recorded. P1 is not the Nginx/PHP/MariaDB site lifecycle, managed DNS/mail, public app deployment, reseller, production installer, or a hosting alpha; those belong to later phases.

### Critical path to a safe test environment

P0 ADR/threat approval → minimum scope and exact candidate test profile → CI/repository baseline → identity/tenant/schema contracts → reviewed auth/session and durable job contracts → reviewed narrow typed-agent/effect-fence contract and required adversarial evidence (a ping-only/no-host-action prototype is not exit evidence) → signed experimental artifact/provenance → clean disposable VM preflight/install/restart/rollback/recovery evidence → explicit P1 exit review. API liveness and UI shell design can proceed in parallel only within their non-privileged constraints. P2 site/DB/SSL/backup end-to-end acceptance remains downstream of P1 and is not counted as P1 test-environment acceptance.
