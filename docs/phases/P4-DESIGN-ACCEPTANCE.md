## Gate and dependency record

The phase index defines P4 as dependent on P2 and P3. P2 is itself gated on verified P1; P3 requires P2's secure site routing, auth/quotas, backups and deploy jobs. The current P1 exit report says P1 is incomplete and P2 entry is blocked. GitHub contains narrow passing P2 lab results and draft P2/P3 specifications, but no accepted P2 or P3 phase gate. Therefore every item below is preparatory; do not implement privileged service mutations or call any acceptance gate passed until maintainers record upstream evidence and security/ADR decisions.

Required handoffs before P4 implementation:
1. P1 exit evidence and explicit P2 entry decision, including approved trust/agent and installer gates.
2. P2 stable site/domain, typed-job, tenant authorization, quota, encrypted secret, backup/restore, and rollback contracts, each linked to exact verified commits/tests.
3. P3 build/runtime isolation, deployment/rollback, secret, and job contracts with hostile-app evidence.
4. A reviewed P4 architecture decision that resolves the relevant proposed ADRs, especially datastore strategy and optional DNS/mail profiles. Existing ADRs are proposals, not approvals.

## Non-overlapping P4 workstreams

### DNS and mail design

- Keep authoritative DNS, external DNS APIs, and mail independently optional capabilities. A basic website profile must continue to work when either is absent.
- Define a provider-neutral typed desired-state contract for zones/records and mail domains/mailboxes. Every operation must bind tenant, domain ownership evidence, capability, idempotency key, expected revision and audit/job identity.
- DNS design must cover authoritative and externally hosted zones, import/export, TTL, DNSSEC state, split DNS, propagation observations, scoped provider credentials, timeout/retry bounds, provider rate limits, drift detection and safe conflict handling. Treat propagation as asynchronous evidence, not a successful API write.
- Mail design must cover Postfix/Dovecot profile isolation, mailbox/alias/forwarder/auto-reply lifecycle, authenticated submission, abuse/rate quotas, queue diagnostics, external relay, TLS, DKIM rotation and SPF/DMARC/MX/PTR checks. State clearly that port 25 and deliverability are provider/network dependent and never guaranteed.
- Avoid storing plaintext provider tokens, mailbox passwords, DKIM private keys or message content in jobs/logs. Specify envelope encryption/key rotation ownership, redaction tests, minimal retention and export controls before implementation.
- Failed DNS or mail dependencies must fail closed for mutations, report partial state and preserve a compensating action. Do not claim rollback for external effects that cannot be reversed; use reconciliation and explicit operator review.

### PostgreSQL and extensions

- Treat PostgreSQL as an optional separately versioned service profile, not an implied replacement for panel metadata storage. The architecture ADR-003 currently leaves that choice unresolved.
- Define tenant database/user ownership, per-database least privilege, credential rotation, extension allowlists by tested OS/package profile, explicit version compatibility, connection/resource limits, backup/restore and upgrade windows.
- Extension installation must use a reviewed package allowlist and declarative typed request; reject arbitrary SQL, package names, filesystem paths and shell fragments from tenant inputs. Separate privileged package changes from tenant database grants.
- Acceptance must cover extension policy denial, unsupported version/OS, partial package failure, role/database isolation, credential rotation, backup/restore, upgrade compatibility and audit redaction.

### Reseller, package and quota boundaries

- Resellers may delegate only capability subsets granted by the platform owner; child accounts must never acquire server-admin or sibling tenant authority.
- Make package limits explicit per resource (sites/domains, storage, database count/size, mailbox count/size, DNS zones/records, API/job rates, runtime CPU/RAM) with documented units, rounding and enforcement semantics.
- Enforce limits at request admission, durable job revalidation and the typed host adapter. UI validation is informational only.
- Define reservation/release semantics for concurrent creates, retries, cancellation, suspension and restoration. Use an atomic reservation or equivalent so two concurrent requests cannot oversubscribe. Define grace/overage reporting; do not silently delete or suspend data when a limit is reached.
- Every object and audit event needs immutable owner/reseller lineage and tenant scope. Test IDOR, changed reseller grants, revoked membership, cross-package transfer and stale queued work.

### Migration dry-run and reconciliation

- Treat every source archive as hostile data. Never execute bundled scripts or trust paths, symlinks, ownership, package metadata, serialized objects or declared sizes.
- Dry-run must be read-only and produce a stable, versioned manifest: source fingerprint, parser version, detected accounts/domains/sites/databases/mail/DNS/backups, conflicts, unsupported items, estimates, required destination capabilities, planned writes, secret reset requirements and warnings. Redact credential values while identifying reset/rotation actions.
- Bound archive entry count, expanded bytes, compression ratio, nesting, path length, parser time and temporary disk. Reject traversal, absolute paths, device nodes, symlink/hardlink escapes, duplicate/conflicting paths, decompression bombs, malformed encodings and ambiguous ownership.
- Stage extracted data under a disposable unprivileged identity and tenant-scoped directory. Verify checksums where present; never restore directly to production paths from an uploaded archive. Staging must carry an opaque migration owner and bounded lease/expiry; crash recovery may reclaim only expired staging proven to belong to that migration, never destination data or another active migration.
- Reconciliation compares desired manifest with destination inventory under a pinned revision, shows create/update/skip/conflict actions and exact pending writes, and requires a fresh review if the source or destination revision changes.
- Execution, once later authorized by upstream gates, should be resumable and idempotent by migration ID and step; record a durable journal, validate post-import services, preserve source, and provide rollback/compensation boundaries. DNS cutover is a separate explicit operator decision with TTL/propagation checks and reversal plan.

For review, model each execution step with durable states `pending`, `applying`, `succeeded`, `retryable_failed`, `needs_review` and `compensated`. Persist `applying` before effects and a verified receipt/postcondition after. Resume may skip `succeeded` only when its receipt and target revision still match; retry `retryable_failed` only when the adapter proves no effect or enforces the same idempotency key. An `applying` step with unknown outcome must reconcile or stop at `needs_review`, never blind-replay a possibly non-idempotent effect. Compensation is a separately journaled typed action with its own result; it is not assumed to reverse external DNS/mail effects.

#### Candidate dry-run report contract (review only)

The following shape makes the already-required manifest fields and safe preview behavior testable. It is a **proposal for review**, not an approved API or execution schema. Keep identifiers opaque, use stable reason codes, and never include passwords, tokens, DKIM keys, serialized source secrets, or host filesystem paths.

```json
{
  "schema_version": "tongpanel.migration-dry-run/v1",
  "source": {
    "format": "cpanel-whm",
    "archive_sha256": "<64 lowercase hex characters>"
  },
  "parser": { "id": "cpanel-whm", "version": "<pinned parser version>" },
  "destination": { "inventory_revision": "<pinned opaque revision>" },
  "generated_at": "<RFC 3339 UTC timestamp>",
  "result": "blocked",
  "inventory": [
    { "source_ref": "<opaque ref>", "kind": "mailbox", "classification": "supported" }
  ],
  "planned_actions": [
    {
      "step_ref": "<stable ref>",
      "action": "manual_review",
      "source_ref": "<opaque ref>",
      "destination_ref": null,
      "reason_codes": ["destination_conflict"],
      "depends_on": []
    }
  ],
  "required_capabilities": ["mail.profile.v1"],
  "secret_actions": [
    { "source_ref": "<opaque ref>", "kind": "mailbox_credential", "action": "reset" }
  ],
  "unsupported_items": [],
  "warnings": [],
  "resource_estimates": { "expanded_bytes": 0, "database_bytes": 0, "file_bytes": 0 },
  "limits_observed": { "entries": 0, "compressed_bytes": 0, "expanded_bytes": 0, "compression_ratio_checks": [{"scope": "TBD per reviewed policy", "compressed_bytes": 0, "expanded_bytes": 0}], "max_nesting_depth": 0, "max_path_length_bytes": 0, "elapsed_ms": 0, "peak_staging_bytes": 0 },
  "plan_fingerprint": "<sha256 of canonical plan fields>"
}
```

`result` is limited to `ready`, `blocked`, `partial`, or `rejected`; `ready` means the preview is fully classified, not that any import ran. Only `ready` may present a candidate create/update plan, and that plan still requires a separate later authorized approval before execution. `blocked`, `partial` and `rejected` reports contain no executable actions. Sort inventory, actions, reason codes and capability lists deterministically. Compute `plan_fingerprint` from canonical source/parser/destination revisions, inventory classifications, planned actions, secret actions, warnings and estimates; exclude `generated_at`, temporary staging names and the fingerprint itself. A new source digest or destination revision invalidates approval and requires a fresh preview. Any later execution authorization must bind the migration ID, plan fingerprint, tenant and destination, the authorizing principal, and the approved action set; immediately before execution, re-read the destination inventory revision and revalidate that principal's current authorization and capability ceiling, rejecting if any binding, inventory revision or policy revision changed. Approval never carries across tenants or silently expands to newly discovered actions. Estimates and limits must state units and reflect observed data, never source-declared sizes alone. `limits_observed` records entry count, compressed and expanded bytes, maximum nesting depth, maximum path length in bytes, elapsed milliseconds and peak staging bytes; derive compression ratio from raw compressed/expanded byte pairs. Before implementation, the reviewed limit policy must define the byte basis and whether the threshold applies per entry, to the aggregate archive, or both; report the scope and raw operands for every evaluated ratio without rounding. Pin inclusive/exclusive threshold semantics in that policy. Use an injected clock and quota-controlled staging so time/disk boundary assertions are deterministic. These fields and policies remain proposed until reviewed.

Candidate contract tests: identical archive bytes, parser version and destination revision yield the same fingerprint; changing source bytes, parser version or destination revision changes it; action dependencies form an acyclic graph and every inventory reference resolves; all planned creates/updates appear in the review list; unsupported/manual-review items cannot be executed; credential canaries never appear in serialized output or logs; limit overflow rejects without an executable plan; a revoked principal, reduced capability, changed tenant/destination, changed inventory revision, or changed policy revision invalidates prior execution authorization; and a dry-run leaves durable destination state unchanged and removes temporary staging on success, failure and cancellation; process termination at each staging checkpoint leaves either safely reclaimable owned staging or no staging, while recovery cannot remove another migration's live stage or destination data.

## P4 acceptance specification (not yet executed)

1. **DNS provider matrix:** in isolated test doubles and a disposable authoritative-DNS lab, verify create/update/delete/import/export, DNSSEC invalid states, stale revisions, idempotent retry, provider timeout/rate-limit, partial failure, propagation pending/failure, credential scope and drift reconciliation. For each pinned profile that exposes TTL, write a record with an explicit configured TTL and capture the requested and provider/authoritative-reported TTL with units, source and observation time; compare pending/observed propagation with that profile's reviewed contract without imposing a universal propagation interval. If TTL behavior is not exposed or its profile contract is unreviewed, report it unverified/unsupported. A tenant without approved ownership proof must not enumerate or change another tenant's zone; rejected attempts leave both the provider fixture and local desired state unchanged and create only a scoped, secret-safe denial record. After a provider reports partial apply, refresh and reconcile actual provider state before any retry; never assume rollback or blindly replay an uncertain write. For split-horizon profiles, first require a reviewed view-selection contract, then assert its configured internal/public responses and that one view cannot enumerate or receive records from the other; without that contract, mark split-horizon unverified. P2 owns DNS-01 challenge/issuance/renewal acceptance; P4 tests zone/provider behavior and only the integration of the P4 DNS adapter with an already accepted P2 ACME flow.
2. **Mail isolation, lifecycle and abuse:** in a disposable mail lab with synthetic identities, verify authenticated send/receive; isolated mailbox, alias, forwarder and auto-reply lifecycle; tenant-scoped IMAP/SMTP setup guidance with secure transport; tenant-scoped webmail session/access if enabled; external-relay success, timeout, credential rotation and denial using a test double; and mailbox migration with credential reset and reconciliation. A tenant must not enumerate, read or manage another tenant's mailbox, aliases, forwarders, auto-replies or queue; denial leaves fixture state unchanged and audit/log output contains no message content or secret. Exercise per-mailbox/domain rate and queue bounds with explicit maximum-count/resource oracles, full queue/disk behavior, relay denial, SPF/DKIM/DMARC/MX/TLS/PTR stale/mismatch results, port-25 unavailable guidance, DKIM rotation and secret/log redaction. For an enabled authentication profile, each controlled positive fixture must report `valid`/`pass` and the expected configured record value; negative fixtures must report the injected stale/mismatch reason. For any explicitly enabled blacklist/reputation diagnostic profile, test listed, not-listed and lookup-unavailable fixtures; show the profile/source and observation time with actionable operator guidance, and report unavailable or unsupported profiles clearly. Do not automatically delist, promise reputation recovery or claim public deliverability. If spam or malware scanning is advertised as enabled, test each separately pinned profile with harmless approved synthetic clean/detection fixtures and an unavailable-engine case; otherwise report that profile as unverified/unsupported. Do not introduce live malicious samples. Keep P2 DNS-01 issuance/renewal separate and make no public deliverability guarantee. Local Postfix/Dovecot, external relay, webmail, spam filtering and malware scanning are separate optional capability profiles; evidence for one does not imply another. Each optional integration must expose tested/unverified/unsupported status and fail closed when a required capability is absent.
3. **PostgreSQL and optional Redis/Valkey profiles:** pin supported versions per OS/architecture; for PostgreSQL prove per-tenant DB/role separation, least-privilege grants, rotation/revocation, allowlisted extensions only, package failure behavior, database count/size limit enforcement, dump/restore correctness and cross-tenant denial. Assert tenant A cannot connect to, enumerate or read/write tenant B's database, and tenant roles cannot escalate to database owner/superuser or grant access beyond their approved scope; denied operations leave grants/data unchanged and produce secret-safe audit. Where an approved tenant-facing operation exposes these fields or entrypoints, reject arbitrary SQL, package names, filesystem paths and shell fragments at the approved typed-operation/package boundary; assert no database, host package or filesystem state changed on denial. Do not invent entrypoints solely to exercise these inputs. Treat Redis/Valkey as separate optional versioned profiles: for any enabled profile, test cross-tenant key read/write denial, credentials/ACLs, prohibited admin or unsupported command denial, resource limits and backup/restore, or report the capability unsupported. Do not infer one datastore's evidence for another. Enablement and the exact command/keyspace model require profile/architecture approval before acceptance.
4. **Reseller, account and quota adversarial matrix:** nested reseller attempts, forbidden role escalation, sibling tenant IDs, team-member grant/revocation, concurrent final-slot allocation, job replay, cancellation/retry races, package downgrade/transfer, suspend/restore, usage accounting, changed ownership and stale jobs. Where SSH/SFTP key or FTP capabilities are enabled, verify tenant ownership, delegated scope, rotation/revocation and secret-safe audit; FTP remains explicitly unsupported unless separately justified and approved. Assert API and typed-adapter enforcement, unchanged state on rejection, attributed audit and no secret values. Once P2's authoritative quota reservation/accounting contract is accepted, enumerate each resource present in the approved package contract (for example sites/domains, storage, database and mailbox counts/sizes, DNS zones/records, API/job rates and runtime CPU/RAM) with its approved units and rounding; verify admission, execution-time revalidation and adapter enforcement at limit and over limit. For resources whose accepted P2 contract defines reservations, assert reservation and usage invariants across concurrent create, retry, cancellation, suspend and restore: no leaked or double-released reservation, no duplicate usage charge, and no unaccounted resource. For other resources, assert only their approved limit and enforcement behavior. Do not prescribe grace/overage policy; reaching a limit must not silently delete data or exceed delegated suspend/restore authority.
5. **Archive adversarial corpus:** traversal, absolute path, symlink/hardlink escape, duplicate entries, oversized metadata, expansion bomb, malformed/truncated archive, forged checksums, unsupported formats, credential-bearing config, duplicate domain/account, database incompatibility and resource exhaustion. For every configured bound (entry count, compressed/expanded bytes and derived compression ratio, nesting, path length, parser time and temporary disk), record observed metrics with explicit units and basis. Pin inclusive/exclusive boundary semantics in the reviewed limit policy, then test at-limit and just-over-limit fixtures according to that policy; if inclusive, at-limit input must be accepted and the first value above the limit rejected with no executable plan; if exclusive, equality must be rejected as specified by policy. Use an injected clock and quota-controlled staging for deterministic parser-time and temporary-disk boundary checks, and derive compression ratio from observed raw byte pairs without rounding; the reviewed policy must define whether ratios are per-entry, aggregate, or both and which byte counts form each operand. Assert bounded execution, no writes during dry-run, precise reject/unsupported report and clean staging teardown. Assert staging is removed or safely reclaimable only after its migration-owned lease expires, and recovery cannot remove another live migration's staging or any destination data.

DNS cutover remains manual. Before admission of any execution job, bind approval to the complete canonical manifest/action set, source/parser identity, tenant/owner, destination/profile and inventory/policy revisions; revalidate current principal authorization and reject stale or changed scope with zero destination writes and no executable job.
