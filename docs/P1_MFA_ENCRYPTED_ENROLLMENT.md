# P1 — Encrypted TOTP seed and trusted-only enrollment prototype

**Status:** Draft review code, not login, not a production service. [PR #29](https://github.com/parmtech/Tong-Panel/pull/29) is stacked on [#28](https://github.com/parmtech/Tong-Panel/pull/28). P0 and ADR-009 remain unapproved.

## Implemented

- Go `MFASecretBox` uses AES-256-GCM with a fresh random 96-bit nonce, 32-byte caller-provided key, versioned envelope (`v1:keyID:base64url`) and authenticated associated data binding to a specific identity and key version.
- Key material is **never generated by default, fetched from the internet, stored in SQLite, logged or returned to clients by this component**. A separate operator-reviewed provisioning, backup, split-key custody and rotation procedure is required. Changing key ID without migration deliberately fails closed.
- SQLite migration v5 adds `mfa_totp_enrollments` with encrypted envelope, identity foreign key, status `pending/active`, 10-minute pending expiry, and activation constraints. No plaintext TOTP secrets or GCM keys are written to the database.
- Trusted-only `BeginTrusted` draws 160 bits from crypto RNG and writes a pending envelope **only if the identity belongs to an active tenant and is enabled**. Another enrollment for the same identity is denied; there is no automatic reset or second seed display.
- Trusted-only `ConfirmTrusted` verifies the pending secret's code and atomically consumes its identity-wide TOTP replay step and activates the enrollment in a single SQLite transaction after rechecking status, tenant and membership.
- `VerifyActive` decrypts only an already activated secret and passes the proof through the existing identity-wide replay ledger. It does **not** issue sessions.
- Tests cover nonce uniqueness, cross-identity ciphertext swaps, key ID/key mismatch, malformed or tampered GCM tags, secret sizes, rejected/enabled/expired enrollments, replay, account suspension/disablement and schema invariants.

## Trust boundary and omissions

These methods are intentionally **internal-only**. They are not an account recovery endpoint or proof of authorization. Do not wire them directly to developer tokens, unauthenticated browser traffic, or public APIs. An approved bootstrap/login flow must first prove current password and/or recent account authorization; the service must use **server-controlled time** and redact the returned seed after a one-time secure enrollment response. Recovery/reset requires stronger verification and revocation of all existing sessions.

Key provisioning and rotation remain unimplemented. The operator must protect key bytes outside backups of the SQLite file, preserve key availability for restores, restrict memory/filesystem access, and design a fail-closed rotation mechanism before deployment. A lost master key makes encrypted seeds unrecoverable; a leaked master key compromises all seeds encrypted under it.

**Crucial atomicity limitation:** confirming enrollment consumes a replay step and activates MFA in one transaction; subsequent `VerifyActive` consumes a replay step separately from session creation. For real login, successful password+MFA, session issuance, role validation and audit record must all be transactionally coupled with explicit retry semantics. Rate limits, generic failure behavior, external TLS origin and Argon2id memory benchmarking remain future security gates.
