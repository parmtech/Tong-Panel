## Finding

A read-only P1 review found a potential current-authorization gap in metadata detail reads. In `internal/api/sites_api.go`, `siteGet`, `siteNginxPreview`, `siteDatabaseCollection` GET, and `siteDatabaseResource` GET check `p.Can("sites:read", p.TenantID)` and then call `SiteCatalog.Get`, `ListDatabases`, or `GetDatabase` with tenant/resource IDs only. These methods filter by tenant/resource but do not recheck current membership or browser session state. By contrast, `siteList` passes requester identity to `ListPageFor` and a cookie `SessionReadProof` to `ListPageForSession`, which checks current membership/session in the read snapshot.

This conflicts with the intended current-membership and cookie revocation/expiry read boundary described in `docs/P1_CURRENT_API_CONTRACT.md` around the site-list contract. Existing API tests found in the review cover anonymous/cross-tenant/role cases, but no regression for removal, role change, or session revocation between middleware authentication and detail catalog read. Exact paths and evidence were checked against local P1 source at commit `4dab4c60cc86186935e9a7d987b9fe1ca97a1f23`.
