## Proposed test architecture (for review)

Use deterministic, local-only fakes for control-plane logic, a disposable isolated network for protocol/integration tests, and synthetic tenant/node data. Every test must record the exact source commit and configuration. Tests involving persistence, time, rotation, revocation, retry, or migration should use controllable clocks and failpoints. No test may use real server credentials, contact a production node, mutate a host, or claim HA from a simulated component. The standalone `prototypes/p5-outcome-model` package explores only conservative outcome reporting after a lost remote response; `prototypes/p5-plugin-capability-model` explores exact-scope plugin authorization and disable behavior. Both are non-normative, offline-only, and have no product-runtime integration.

### Candidate fault-injection oracle for scenario 5 (not a protocol contract)

| Injected failure point | Coordinator's safe view | Candidate retry/recovery rule |
|---|---|---|
| Before dispatch is attempted | Not dispatched | Dispatch only after current authorization and node eligibility are checked. |
| Dispatch attempted; no response received | Unknown | Reconcile by stable operation identity. Replay only the same key, node, tenant, action and immutable request when worker-side deduplication is durable. |
| Node accepted the operation; acceptance response lost | Unknown | Do not issue a new operation identity; query/replay under the reviewed deduplication contract. |
| Effect may have happened; completion response lost | Unknown | Do not infer failure from timeout or node offline status. Verify/reconcile before terminal success or another effect. |
| Worker reports completion but external effect is not verified | Unknown | Keep a pending/uncertain status and expose the missing verification evidence. |
| Required external effect is independently verified | Succeeded | Record verification source, timestamp, operation identity, and actor; late stale responses must not downgrade the record. |
| Node revocation occurs while disconnected or work is in flight | No new dispatch; in-flight outcome remains unknown until resolved | Reauthorize queued work on reconnect. Apply the reviewed cancellation/quiescence rule to running work; never treat disconnection as cancellation proof. |
| Worker restarts or restores state after an uncertain dispatch; same-key replay and a delayed duplicate/stale response follow | At most one effect; an uncertain result remains Unknown until independently reconciled, and stale evidence cannot downgrade a newer verified result or supersede revocation | Retain immutable operation/request digest and idempotency key, worker dedupe record before/after restart or restore, dispatch/effect counts, response timestamps/order, authorization/revocation version, verifier result, coordinator state transitions, and audit correlation. Persistence and verifier mechanisms remain subject to review. |

The implementation must define a correlation mechanism that makes duplicate, delayed, and reordered responses attributable to the same operation without allowing stale evidence to overwrite a newer revocation or verified result. Selection of that mechanism, the authoritative effect verifier, and the exact state names require P0/P1/P5 review. The table is an acceptance-design aid only.

## Phase 5 acceptance scenarios

### Node identity, enrollment, rotation, and revocation

1. **One-time enrollment:** accept one valid, short-lived enrollment proof; reject reuse, expiry, malformed proof, wrong control-plane audience, and a proof issued for another node. A failed attempt must not leave a registered or partially trusted node.
2. **Mutual identity:** accept only the expected node identity and trust root; reject unknown, expired, not-yet-valid, wrong-purpose, and wrong-node certificates. Do not fall back to bearer-only or unauthenticated transport.
3. **Rotation:** exercise overlap and retirement windows using a fake clock; prove old material is rejected after retirement and no rotation secret is logged or persisted in plaintext. Retain a synthetic secret marker, redacted log/storage scan results, and proof that the marker is absent from logs and persisted state.
4. **Revocation:** revoke a node while connected and while disconnected; immediately stop new control-plane dispatches, and after reconnection deny new jobs and credentials. Reauthorize queued jobs at execution. Exercise the reviewed policy for already-running work; if its effect cannot be stopped or verified, report unknown rather than cancelled or successful. Verify stale cached authorization cannot restore access, revoked authorization denies replay, and revocation is auditable. Do not treat a disconnected node as proof that in-flight work stopped.
5. **Control-plane partition:** partition control-plane-to-node traffic before, during, and after a lease. Verify no ghost-success, no unbounded authorization lease, explicit unknown outcome for uncertain effects, and safe reconnection reconciliation. Replay after a lost response must retain the same idempotency key, target node, tenant, action, and immutable request; changed bindings or missing durable node deduplication must deny replay. The offline candidate classifier is in `prototypes/p5-outcome-model`.
6. **Node partition/offline:** mark health and job state honestly when a node is offline; retries must not duplicate non-idempotent work. The UI/API must distinguish unreachable, pending, failed, and externally verified success.

### Authorization and placement

7. **Cross-node/tenant denial:** submit a valid user/job for a different node or tenant and assert denial before dispatch, no metadata leakage, no remote side effect, and an attributed audit record.
8. **Policy change in flight:** narrow permissions or remove placement eligibility between enqueue and execution; execution-time authorization must deny, with a stable reason code and no arbitrary command path.
9. **Placement determinism:** given inventory, labels, constraints, health, and capacity, verify deterministic eligible-node selection; unknown/stale inventory and malformed or internally conflicting constraints fail closed, while a valid request with no matching candidate remains unplaced. The offline candidate model in `prototypes/p5-placement-gate-model` now exercises a lexicographic node-ID tie-break, exact environment/label matching, known sufficient abstract capacity, and maintenance-window eligibility. It does not reserve capacity, provide fairness, establish inventory authority, or implement a product scheduler.
10. **No shell escape:** fuzz the typed job/action protocol with unknown action, extra fields, path/argument injection, oversized frames, duplicate keys, replayed IDs, and malformed encodings. No generic shell/exec operation is accepted.

Scenarios 29–30 extend this area with scheduled maintenance and staging/production separation.

### Migration and recovery

11. **Staged migration:** create identified synthetic app/database backup artifacts bound to the same source snapshot and tenant/account owner, record their identities and digests, transfer and restore only to the authorized matching owner at the destination, then verify integrity and application-level invariants before cutover. Reject missing, stale, or mismatched ownership before restore/activation. Preserve source authority/state until explicit validation.
12. **Cutover interruption:** inject failure at every stage (snapshot, transfer, restore, validation, DNS/route and TLS/certificate switch, source retirement). Verify the destination hostname and trusted certificate chain before reporting cutover; report the last verified stage and avoid claiming success when outcome is unknown.
13. **Rollback:** before and after cutover, exercise rollback with writes on both sides. Detect divergence and require reconciliation rather than silently discarding data. Verify documented RPO/RTO measurements are derived from observed tests.
14. **Credential rotation during move:** rotate/revoke node and service credentials during transfer; verify authorization separately at each migration stage/action, only the authorized stage continues, and all temporary material is removed or invalidated on abort.
15. **Recovery after process restart:** restart coordinator and node agents at each migration checkpoint, including after route/TLS cutover and during or after rollback; reconcile durable state without duplicate cutover, premature source retirement, or loss of audit lineage.

### Plugins, marketplace, and ecosystem

16. **Manifest and signature policy:** reject unsigned, untrusted, mutable/unpinned, expired, wrong-target, downgraded, or incompatible plugin artifacts before installation. Verify dependency and licence metadata is present and reviewable.
17. **Capability sandbox:** grant a plugin only declared scoped capabilities; prove denied node, tenant, file, secret, network, and API access cannot be reached through direct or confused-deputy paths. The offline candidate model checks exact plugin/install/tenant/resource/capability matching only; it is not sandbox evidence.
18. **Disable and uninstall:** disable/revoke capabilities immediately, preserve user-owned data with an explicit recovery path, and prove panel boot and unrelated plugins continue. Uninstall must not delete unowned data. The offline prototype tests only that an in-memory disabled grant denies repeat requests; persistence, cache invalidation, data preservation, and boot behavior remain untested.
19. **Update and rollback:** stage a signed update, validate compatibility, inject failure, and restore the prior known-good version without restoring revoked permissions or secrets.
20. **Registry outage/compromise:** test unavailable registry, stale metadata, key revocation, and an artifact whose digest differs from reviewed metadata. Fail closed and preserve audit evidence.

### Usage, billing integrations, and HA claims

21. **Usage accounting:** reconcile synthetic usage across node restart, delayed/offline reports, duplicate events, clock skew, and tenant transfer. Keep source measurements and derived totals attributable; do not emit billing actions from unverified usage.
22. **External billing/provisioning:** use a fake provider and signed webhook fixtures; test replay, duplicate delivery, timeout, reordered events, and idempotent reconciliation. Billing failure must not silently grant privileges or destroy hosted data.
23. **Mirrored services:** for each proposed DNS/mail/database topology, declare consistency and failure semantics, then test split brain, stale replica, quorum loss, failover, and recovery. Document when an operation is unavailable or read-only.
24. **HA boundary:** publish no HA claim unless workload-specific failover and recovery tests establish explicit topology, failure domain, measured RPO/RTO, and known limitations. Management across several nodes alone is not HA evidence.

| Notification consumer is offline, times out, or acknowledges late | Preserve an observable pending/delivery-failed state and apply the reviewed retry/retention policy without turning delivery into authorization or billing. | Fake-clock trace, attempt IDs, acknowledgments, resulting delivery state, and retry/expiry decision. |
| Audit export is paginated while records are added, filtered, or redacted | Enforce tenant scope and approved filters; retain deterministic cursor/completeness semantics, redact protected fields, and make retention exclusions explicit. | Synthetic event inventory, page/cursor sequence, expected/exported IDs, redaction assertions, and retention policy/version. |

#### Review-only evidence contract for scenarios 23–24

For each service and supported topology, the test record should name the exact implementation/configuration, node and witness roles, independent failure domains, authoritative write path, consistency guarantee, and supported read/write behavior. Before fault injection, record which observations count as an acknowledged durable write and define a service-specific correctness oracle and health check for before, during, and after partition, promotion, and recovery. Examples include authoritative DNS answers and serial convergence; mail queue, delivery, and duplicate-message checks; and database transaction/replica consistency. Retain expected and observed values at each stage, not only a generic health result. These are evidence fields, not a prescribed topology or replication algorithm.

| Fault or claim | Required observation and evidence | Claim limit |
|---|---|---|
| Control-plane or inter-node partition | Record reachability in each direction, authoritative role before/during/after partition, accepted/rejected writes, stale reads, and the evidence used to prevent or detect competing writers. Record promotion/demotion decision, authorizing actor/policy, role or term, and fencing evidence; rejoin must reconcile or quarantine divergence explicitly. | A simulated partition validates only the tested harness/configuration; it does not prove every network or host failure mode. |
| Stale replica, quorum loss, or witness loss | Record which reads/writes remain available, what authority is retained, whether promotion is denied, and how stale data is detected before resuming writes. | Do not infer safe promotion or consistency from node health alone. |
| Failover and recovery | Record fault injection time, detection/decision/recovery milestones, promotion authorization, role/term and fencing evidence, service-level verification, acknowledged writes compared with recovered data, and any manual action or data repair. Repeat across each claimed failure domain and supported topology. | Report observations and sample count; one successful drill does not establish a general availability percentage. |
| RPO/RTO statement | Derive RPO from the observed gap between acknowledged durable writes and verified recovered state; derive RTO from injected failure to independently verified service recovery. Include workload, topology, repetitions, percentile or range, and exclusions. | Publish only measured scope and conditions; label targets separately from observed results. |
| Management availability vs service HA | Test control-plane loss separately from workload service behavior, including operation queueing, authorization expiry/revocation, and reconciliation on reconnect. | Multi-node inventory/orchestration alone supports only a management capability claim, not workload HA. |

25. **Marketplace moderation:** keep an artifact unavailable for installation until the configured review gate accepts the exact version and digest; reject incomplete license, provenance, signature, or permission declarations without activation. Verify review, rejection, and later revocation are attributable and do not mutate existing installs silently.
26. **Dependency update alerts:** surface a synthetic advisory for the exact affected dependency/version range to the correct tenant/operator; deduplicate repeat feeds, preserve source and freshness, and do not silently update packages or grant new privileges. Conflicting or stale advisory data must be labeled uncertain rather than presented as current fact.
27. **Deprecation and retirement:** identify affected installations, publish the reviewed support/deprecation state and migration path, and test upgrade/removal with synthetic user data. Preserve an export or recovery path; do not silently remove data, restore revoked permissions, or prevent panel boot if a plugin is retired.
28. **Recipe/plugin boundary:** verify a declarative app recipe cannot obtain executable plugin capabilities or arbitrary host actions. A package requiring executable panel code must pass the separate plugin review, signature, and scoped-capability checks before any such code is activated.

#### Review-only marketplace and lifecycle evidence for scenarios 25–28

Before implementation, owners must approve the moderation authority, review record, advisory sources/freshness, deprecation lifecycle, and separation between declarative recipes and executable plugins. These cases specify observable checks without choosing a marketplace operator, vulnerability feed, package format, or retirement schedule.

| Fixture or fault | Expected test result | Evidence to retain |
|---|---|---|
| Artifact is pending review, rejected, or later revoked | Deny new activation until the exact version/digest is approved; keep decisions attributable and do not silently alter existing installations. | Moderation decision/review ID bound to package, version, target, and approved digest; install request and staged artifact IDs/digests; reviewer/decision state, activation result, and active-version inventory proving only the approved digest can activate. |
| Dependency advisory is repeated, stale, contradictory, or does not match the installed version | Deduplicate matching notices, preserve source/freshness, scope notices to affected installations, and label unresolved evidence; no silent update or privilege change. | Advisory IDs and digests, dependency lock/installed versions, tenant fixture, intended recipient tenant/operator IDs, timestamps, emitted notice IDs, delivery/visibility results, proof unaffected recipients received none, and action audit. |
| Deprecated plugin has user-owned data or a proposed replacement | Identify affected installations and a reviewed migration/export route; preserve data through upgrade/retirement and keep unrelated panel/plugin boot healthy. | Synthetic data inventory, expected and discovered affected installation IDs, deprecation state/version, migration/rollback trace, export verification, and boot/health result. |
| Declarative recipe attempts to request executable plugin capability or host action | Reject or route to the separate reviewed executable-plugin path before activation; recipe metadata alone cannot grant that capability. | Recipe and plugin fixtures, schema/decision trace, denied side-effect checks, and reviewed permission record. |

29. **Scheduled maintenance:** use a fake clock to exercise entry to and exit from a maintenance window. Apply the reviewed disposition to queued/running jobs, deny new placement on affected nodes during the window, and require fresh health/eligibility evidence before returning a node to placement. Unspecified or conflicting disposition fails closed and is auditable. The offline candidate model exercises only eligibility timing.
30. **Staging/production separation:** use synthetic nodes, tenants, jobs, and credentials labeled for separate environments. Placement, secret use, migration, and release actions must remain within the declared environment; missing/stale environment identity or a cross-environment request is denied before dispatch without leaking inventory. The offline candidate model covers exact string matching only, not credential or data-path isolation.

#### Review-only maintenance and environment evidence for scenarios 29–30

Before implementation, approve maintenance entry/exit semantics, timezone/clock authority, queued and in-flight job disposition, environment-label authority, and which identity/credential bindings enforce staging versus production boundaries. Tests should use synthetic resources and establish no cross-environment dispatch, secret use, or data movement without choosing a scheduling engine or deployment topology.

| Fixture or fault | Expected test result | Evidence to retain |
|---|---|---|
| Job is queued before maintenance begins; a dispatch races with the window start | Follow only the reviewed disposition; do not place new work on the affected node after the authoritative window begins. | Fake-clock timeline, schedule revision, queue/dispatch order, eligibility decision, and audit record. |
| A new placement request arrives while the maintenance window is active | Deny placement on the affected node and do not dispatch the job. | Fake-clock reading, active window/schedule revision, eligibility decision, zero-dispatch counter, and audit record. |
| A job is already running when maintenance begins | Apply the reviewed in-flight disposition; record effect acknowledgment and independently verified final state. A timeout or disconnect alone does not prove cancellation. | Running-job/action ID, maintenance decision/acknowledgment, last verified effect, timeout/disconnect trace if present, final-state verification, and audit correlation. |
| Maintenance ends but node health or inventory is stale | Keep the node ineligible until refreshed evidence satisfies the reviewed return criteria. | Window close time, health/inventory versions, refresh result, and placement decision. |
| Staging request targets a production-only node/credential, uses an expired/revoked credential, or environment identity is missing/stale | Deny before dispatch or secret lookup/access; do not expose production inventory details to the staging caller. | Synthetic principals/resources, environment labels and versions, credential ID/version/status and environment binding, denied response snapshot/redaction assertion, inventory-access counter, secret-lookup/access and dispatch counters. |
| Migration/release attempts to cross environments | Require an explicitly reviewed migration path with separate authorization and verified data/credential handling; reject unapproved direct crossover without changing either environment. | Source/destination environment fixture, authorization context, denied response/redaction assertion, inventory-access counter, zero secret-lookup/dispatch/bytes-transferred counters, transfer records, before/after source and destination state digests, rollback/recovery result, and verified denied/approved outcome. |

## Review-only evidence contract for platform expansion

The Phase 5 plan allows additional Linux distributions and arm64 only after separate automated verification. Treat every OS/release/architecture combination as an independent target; this contract defines evidence to review and does not add a supported platform or authorize implementation.

| Evidence item | Required record or result |
|---|---|
| Exact target | Distribution and release, architecture, kernel/ABI where relevant, runner or VM image digest, and the artifact/source commit under test. State whether execution is native or emulated. |
| Scope preflight | Check the declared support matrix before host mutation. An unsupported tuple must fail closed before installation or other host effects. |
| Lifecycle | On that tuple, run the applicable automated install, upgrade, interruption, rollback, and recovery scenarios from the reviewed plan. Record each scenario separately, including cleanup and restored-state verification. |
| P5 behavior | Run the applicable P5 protocol, authorization/revocation, migration, plugin, API, and recovery scenarios against synthetic fixtures on the target. Identify exclusions rather than inferring behavior from a different target. |
| Architecture evidence | Use hardware-native execution for a native-architecture claim. If emulation is used, label it and limit conclusions to the emulated environment; it cannot establish native hardware acceptance. |
| Reproducibility | Retain the workflow/run ID, exact source and artifact digests, fixture/version, commands, logs with secrets removed, observed result, retries/failures, cleanup result, and reviewer per tuple. |

Passing on one distribution, release, image, or architecture does not transfer to another. No platform-support expansion should be claimed until each proposed tuple has its own reviewed evidence package and the applicable phase entry gates are satisfied.

## Evidence and completion record

Each accepted test should retain: scenario ID, source commit, test harness/environment, synthetic fixture description, expected and observed result, logs with secrets removed, cleanup result, and reviewer. Failures and retries remain in the record. A P5 release decision additionally requires the plan's partition/offline/revocation, wrong-node/tenant, migration consistency/rollback, plugin disable/recovery, supply-chain, and HA-boundary criteria to pass on the reviewed implementation. No completion claim is made by this specification.
